LVGL Memory Estimator

How much memory might your HMI need? Start with a screen, add your assets and choose the system features. Get a transparent RAM and storage budget.

01 / Screen & rendering

Pixel buffers use 4-byte row alignment. Count only additional framebuffers: shared LVGL / scanout buffers must not be counted twice.

02 / Images & assets

Files stay in your browser. Images: PNG, JPEG, WebP, BMP. Videos: browser-readable MP4 / WebM. No upload to a server. Add manual estimates below for fonts or other formats.

    Decoded images are budgeted as 32-bit pixels. The largest resident images are included in RAM. Compressed file size is storage, not decoded RAM. Manual file size adds to imported files.

    03 / Video

    Video is a separate decoder / platform capability, not implied by LVGL. Frame and decoder budgets are editable; codec, GPU and driver allocations need platform validation.

    04 / System & headroom

    Presets are illustrative planning allowances, not measured OS requirements. Runtime includes heap, objects, stacks, fonts, application and OS. Adjust to your platform; storage excludes logs, updates / A-B partitions and filesystem overhead unless you add them.

    Calculation method & sources

    Display RAM = aligned row bytes × rendered rows × buffer count. Software rotation adds one rotated tile (partial) or frame (direct / full). Images use decoded width × height × 4, with aligned rows. Video adds decoded reference surfaces plus your decoder / conversion allowance. System budgets are added once, then planning headroom is applied. Units are KiB / MiB (1024-based).

    Hardware rotation adds no extra software scratch buffer in this model. Decoder zero-copy sharing, GPU textures, extra draw layers, effects and animation peaks may change the result.
